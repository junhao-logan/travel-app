# ADR-0004：认证方式
- 状态：已采纳
- 日期：2026-11-22
- 背景：网页端为主的产品（v1 不做原生 App），需要安全的登录态管理，并且要支持"登出所有设备"和封禁账号后立即失效。
- 选项：
  - A：服务端 session（存 Redis）+ httpOnly cookie：浏览器只保存一个随机 session ID，用户信息存在服务端；可以随时撤销，前端脚本读不到 cookie（XSS 偷不走）/ 每个请求查一次 Redis；需要防 CSRF（SameSite + CSRF token）
  - B：JWT（access + refresh）：无状态、适合多端和服务间调用 / 签发后在过期前无法撤销，要撤销就得另建黑名单；常被存在 localStorage，XSS 风险更高
  - C：托管认证服务（Auth0、Clerk 等）：不用自己实现 / 按用户数收费，用户数据在第三方，迁移困难；与 M1 "自己写账户样板模块"的路线冲突
- 决定：A（服务端 session 存 Redis + httpOnly、Secure、SameSite cookie）
- 理由：
  1. 网页为主，JWT 的多端优势用不上。
  2. "登出所有设备"和"封号立即生效"是产品要求，A 天生支持（删掉服务端 session 即可）。
  3. 网页应用中最主流、OWASP 推荐的做法；主流 Web 框架默认方式。
  4. 使用已定的 Redis，不引入新服务，免费。
- 代价：
  - 每个请求多一次 Redis 查询（亚毫秒级）。
  - 必须实现 CSRF 防护，并在 M1 中测试。
  - Redis 成为登录态的依赖：Redis 数据丢失 = 所有用户需要重新登录（可接受，不丢业务数据）。
- 具体参数（cookie 名、过期时间、密码哈希算法、限流）在 M1 方案里确定。
- 以后什么情况下重新评估：要做原生 App 或开放 API 给第三方时，写新 ADR，在 A 的基础上为这些客户端增加 token 认证，而不是替换 A。
