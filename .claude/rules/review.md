# 审查流程（每个功能完成前做两次审查）

尽量用子代理执行，让审查在独立上下文里进行，不受实现过程的影响。审查只出报告，不改文件。
两个审查的输出都用中文，分为：**必须修**（file:line、问题、修复方法）、**建议**、以及各自的附加项。没有问题就直说，不要编造问题。

## A. 安全审查
1. 运行 `git diff main...HEAD`，读改动涉及的文件。
2. 对照 `docs/security-checklist.md` 逐条检查每条改动路径，重点：
   - service 层的资源归属检查（IDOR），包括列表、搜索、分享接口
   - 私有内容能否通过任何接口泄露
   - 上传校验（类型、大小、magic bytes、EXIF 清除、presigned URL 限制）
   - 响应或日志里有没有密钥、调试信息、堆栈、个人信息
   - 认证和上传接口有没有限流
   - 权限和错误路径有没有测试
3. 附加输出：**清单逐项** → 通过 / 不涉及 / 有问题；"必须修"的问题要写出具体的攻击或失败场景。

## B. 代码审查
1. 运行 `git diff main...HEAD`，读改动涉及的文件；读 `CLAUDE.md`、`docs/architecture.md` 第 2 和第 7 节，以及 users 样板模块（存在之后）。
2. 检查：
   - 分层：router 里没有业务逻辑和数据库访问；只有 repository 查数据库；返回 schema 而不是 ORM 对象
   - 约定：错误格式、cursor 分页、UUID、UTC 时间、结构化日志
   - 和样板模块的一致性（结构、命名、测试风格）
   - 测试：覆盖正常路径、错误路径、权限；测试有实际意义
   - 前端：加载 / 空 / 错误状态、移动端布局、使用生成的 API client
   - 文档：roadmap / architecture / CLAUDE.md 是否已更新
   - 有没有未经 ADR 采纳的新依赖
3. 附加输出：**超出范围的改动**（方案里没有、却被加进来的东西）。
